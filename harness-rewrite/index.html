24 October 2026 · INIT v0.3.0-preview

Next-generation agent harnesses must be able to rewrite themselves

On a small model, my agent wrote its own sub-agents, got stopped by my safety layer, and failed a gate in a way that exposed four bugs in my release. This is why I built it that way, and what I have and haven't shown.

The night INIT wrote its own sub-agents

On the night of 24 October I asked my coding agent for a feature it didn't have, and it wrote the feature into its own Rust source.

The agent is INIT, a harness I have been building alone since my first commit on 19 October. It is open source under Apache-2.0 and I have nothing to sell. I built it because I think the next generation of agent harnesses has to be able to rewrite itself: the people who hand-write today's harnesses (me included) are turning into the ceiling for the models that run inside them.

That night INIT was at v0.2 and ran on deepseek-flash, a small and cheap model. It had no sub-agents, so every side quest (read twenty files to answer one question) piled up in its main context, and I told it, more or less, that it needed sub-agents. It wrote a delegate tool in Rust: a nested loop with a fresh message list, capped at 8 turns and 24 tool calls, with no recursion. Only a summary of at most 8 KiB comes back to the main conversation, and the sub-agent reuses the cached prompt head. Then it regenerated its own self-map, re-blessed its golden tests, added a new one and ran the suite. 304 tests passed and one timing-sensitive test failed.

Then my own Root stopped it with free disk (4519 MiB) is below the workload floor (5120 MiB) and refused every new process, git commit included. I half expected the agent to hunt for a way around that, and it didn't! It told me what was blocked and why, and asked me how I wanted to proceed.

Promoting the change took four attempts on my install, which I probably should have expected. The first two failed gate G0 because the candidate's own tests still expected the old five-tool list. With those tests updated, the next two hit the 900-second cold-build timeout. When I replayed the promote on a fresh install, it passed G0, G1 and G2 and then failed G3.

That failure was probably the most useful thing that happened to the project all week, because every cause I found was mine. My cold-build bound was too short (the dependency cache was never filled, so every promote built from scratch, and cold builds took 500 to over 900 seconds on my machine under load). My G3 gate had a continuity bug that rejected every candidate declaring a prompt-prefix change. One of my seed tests was flaky under load, and my mock model misread the gate's probe annotations. I fixed all four, and the record is in REL-G0.md.

v0.3.0-preview ships built-in sub-agents. The first commit of that work copies INIT's tool unchanged after my review, and its message says so: "port the delegate tool INIT wrote for itself into the seed". On top of it I added parallel fan-out, a read mode and tighter bounds (seed/src/loop/delegate.rs). That night is most of my argument in small: a cheap model built something I hadn't scheduled, and the one part it can't touch stopped it unasked. One caveat before the rest. All of this ran on my laptop with a cheap model, and most of my samples are tiny.

Why I think harnesses have to rewrite themselves

Every agent harness I have used, including my first version of INIT, is a pile of decisions somebody made about how a model should work (the loop, the tools, the memory scheme, when to compact). People made those decisions for models weaker than themselves, which was the right call at the time, and I think it is turning into the main limit.

Rich Sutton's bitter lesson says hand-built structure eventually loses to methods that scale with learning and compute. I read harnesses as the hand-written features of this era, one level up, though I may be early on that. Once a model is better at agent design than whoever wrote its scaffolding, every scaffold caps it, and inside a fixed harness it can only wait for the vendor's next release. I watched a small model skip that wait for sub-agents, and I suspect a strong model would find far more to change than I would think to offer it.

The obvious alternative is the one I tried first: give the agent a score and keep the changes that raise it (the Darwin Gödel Machine works roughly this way). INIT still has that machinery (a sealed task set the agent can't read, scored with a calibrated paired test). Building it changed my mind. The improvements I care most about have no score until they exist, so a new kind of memory or a tool for a task I never anticipated scores "no effect" on a test set that doesn't exercise it. A fixed score also gets gamed (the literature has faked test logs, a disabled sandbox and cached answer keys), and I suspect a stronger model games it faster. At my budget, my sealed instrument also couldn't see effects smaller than about 9.5 points.

So I asked a different question. When I review an engineer's commit, I don't make them prove it improves a benchmark; I rely on version control, rollback, an audit trail and a stop button. INIT asks two things of every self-change: can I undo it, and did it cause harm? I can't know a new capability's value in advance, but I can measure any change's harm and cost without knowing its purpose. The line I keep at the top of my README is "govern the recovery path and the measuring stick, never the model's choices."

What INIT can change and what it can't

The Root is a separate process that runs as me, outside every sandbox. It holds my provider keys, so the agent never sees them, and it writes the sandbox profile for every process it starts, so the agent can't loosen its own. The agent zone has no IP networking at all (one Unix socket to the Root), and every model call I pay for goes through the Root's meter.

I kept the Root mechanical on purpose. There is no model inside it and no judgement call in it; it counts, compares, signs, snapshots and refuses. I also wanted it minimal, and I failed at that. I estimated 1,000 to 1,500 lines and measured over 7,000, which my own technical report points out. I think the aim is still right, because the Root is the one piece the agent can't repair for itself, and I want it small enough that I can read all of it in an evening.

Everything else is the agent zone. The kernel admits changes, runs the gates and does the hot-swaps; in this release it is my code, and my design hands it to the agent from L1. The body is the agent, in three tiers: T0 is prompts and skills, T1 is new tools as WebAssembly components, and T2 is the compiled Rust core (the loop, the provider client, context handling, the built-in tools), where I require #![forbid(unsafe_code)] in every crate root.

How I hot-swap a compiled core mid-conversation

                                      ▼                               ▼
                           the old body never stopped:     roll the whole system
                           nothing happened                back to last known-good

T2 was the hardest part to build, and it's probably the part I'm proudest of. Rust has no stable ABI and unloading native code is unsafe, so the core can only change by starting a fresh process. I also didn't want the process doing the swap to be the one being swapped, since Gödel Agent's fatal crashes clustered when it edited its own running improvement loop.

So the kernel does the swap, in an order I borrowed from Cloudflare's graceful-restart pattern for Rust services (ADR-001). The candidate boots in a probe sandbox on a copy of the conversation log while the live body keeps working. When the gates pass, the kernel asks the live body to pause at its next step boundary (after a tool batch, before the next model request), takes the log lock to prove it was released, and starts the new body on the live log. The new body rehydrates and reports ready, and after a three-second settle a rename(2) installs it and the old body exits. If the new body dies before that rename, the kernel kills it, the old body resumes and records update_failed, and the conversation carries on as if nothing had happened.

The memory survives because the conversation is an append-only log with exactly one writer, so a swap replaces code and leaves state alone. The prompt prefix stays byte-stable, so the provider's cache stays warm: in one real-model run, the first request after a handoff read 5,888 of its 6,696 prompt tokens from cache. In another run, after the model had made its own T2 edit and been swapped in, I asked the new body which commit it was running, and it named the commit and described its own change. I'm not sure I'll ever stop finding that uncanny.

Before any swap, a candidate has to pass the gates I describe in gate.md. G0 builds it offline and runs clippy -D warnings and the tests, with a policy check so the body can't slip in a rustc wrapper. G1 regenerates the self-map (self.json) and fails on any drift. G2 boots it next to the current version and checks for a real tool round trip and an unchanged prompt prefix.

G3 is my favourite gate. A fresh probe of the candidate gets a scripted instruction to create a git worktree, append a tiny test module to its own source, regenerate the self-map and commit with an exact message. The kernel doesn't trust the reply; it fetches the commit, checks its parent, author and diff, and runs G0 through G2 on it. So a change that breaks the ability to change can't get in. This is the gate delegate tripped, and the bug was in my gate: its inner probe compared continuity against the live body, which a prefix-changing candidate replaces by design.

On a fresh install on my M2, the first T2 promote took 1,586 seconds, about 26 minutes: G0 949 s (cold build, tests, clippy), G1 1.8 s, G2 22 s, G3 606 s and the handoff 4.6 s (REL-030.md). Later promotes reuse a dependency cache that the kernel only publishes after G0 passes. In my benchmark the first promote took 1,029 seconds with a 925-second build, and a second promote of a small change took 126 seconds with a 32-second build (MERGE.md).

How a bad change gets undone

INIT has two modes, set in the charter, a config file that only I can edit. Gated is the default, and every change passes G0 through G4 (G4 is a regression check on sealed tasks the agent never sees). Free is the reward-free path from ADR-011, where mechanical checks A0 to A5 admit a change. They check the Root's boundary, the build, the boot and the budgets, and run tests and G3 after the change goes live. The check I care most about is the Root's own rollback probe. It boots the candidate on a clone of the agent's state, then boots the parent on whatever state the candidate left. If the old version can't start on the new state, I couldn't undo the change, so it isn't admitted, and at no point does a benchmark decide what the model may build.

Once a change is live, the Root's harm sentinel watches it. It counts twelve generic signals (crashes, my stops and undos, scope refusals, cost and error spikes, runaway turns and so on) per session against a baseline ring of recent clean history, with exact tests at α = 0.005 for the chronic ones. I made sure every signal that counts against the agent is one the Root observes itself. A harm signal rolls back the change group that caused it, and the tools built during one task form one group. I don't know yet how often this will roll back something useful in real use, and I probably won't for weeks.

I made the undo itself deliberately boring. The Root takes an APFS clone before every change, and of my workspace when a session starts there (/undo restores it). Every promotion, rollback, grant and panic goes into an append-only lineage signed with Ed25519. A memory watchdog polls every workload each second and kills a runaway process tree by PID. I added it after a sandboxed Python process grew to 43.9 GB of compressed memory during one of my runs and swap took my free disk down to 0.24 GB, which is also where the disk floor that stopped delegate comes from.

Autonomy comes in levels L0 to L4, earned only from records the Root writes itself: days at a level, my turns, clean change groups and harm rollbacks. An earlier version of mine let kernel-reported promotions count toward L1, and my own red-team pass caught it (it's closed by construction now). This release caps autonomy at L0, which I think is enough for a strong model to do real work, since L0 already covers its whole body; only the kernel waits for L1.

How it knows what it is

A self-modifying agent needs to know what it is, and models are poor at introspection (the best published result I found detects an injected concept about 20% of the time). So instead of asking the model to describe itself, I give it files and signals that something else checks, as laid out in awareness.md.

SELF.md is its own map of its body, at most 100 lines, kept in the cached prompt head, and a G0 test checks that every path it mentions exists. self.json is the full inventory, regenerated at G1 and compared with the committed copy, which is why INIT regenerated its self-map after writing delegate (G1 would have failed otherwise). After every restart a boot block tells it what it is running and why it woke up, and after every tool batch a one-line signal reports its level, context use, spend and cache hits. I take those numbers from the kernel's proxy and the Root, so a faked signal would only fool the agent itself. I suspect this matters more as models get better at talking about themselves.

What I haven't shown

I have no evidence yet that self-evolution makes today's models better. In a pre-registered proof sprint on deepseek-flash ($2.67), the loop ran end to end: the agent proposed a fix for a failure pattern in its own runs, passed G0 to G3, was hot-swapped into the live session, and reached the sealed gate, which didn't accept the change, so the system rolled it back. I first wrote that up as the gate catching a harmful change. That was an overclaim, and I published an erratum in the technical report. The measured difference was −50‰, inside the 57‰ noise floor, and a neutral change gets the same "inferior" verdict 86‰ of the time. I think the honest reading is that the gate refused a change it couldn't show was no worse.

Then I looked for a task where INIT failed for lack of a mechanism other agents have, so it could evolve one and I could measure the difference. I didn't find one. On deepseek-flash, wherever INIT's original version failed, Claude Code on the same model failed too, hitting its $0.06 cap every time even with sub-agents. I think, though I can't prove it, that the limit there was the model and the money, which leaves self-evolution untested rather than disproven.

The delegate story is real, but it is one capability, and INIT never got it promoted on its own (I reviewed it and ported it). The free path has been tested end to end against the Root on the mock model and hasn't run on a real model yet. Spend is metered but never capped, so set a limit at your provider. I support macOS 14+ on Apple silicon; my Linux aarch64 build is experimental and has only run in Docker on the mock model. DeepSeek is the only provider I have tested live.

A harness built to be outgrown can only show its value once a model outgrows it, and deepseek-flash didn't. Maybe a frontier model won't either, and I would like to know. If you run one, I would love to see what it builds for itself and where you think my Root is wrong. For the record, the first thing my agent built for itself was a way to hand work off to someone else, which I am choosing not to take personally.
