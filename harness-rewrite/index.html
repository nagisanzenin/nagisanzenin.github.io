Next-generation agent harnesses must be able to rewrite themselves

Why I think the harness is the last hand-written layer of an agent, why I let mine rewrite itself without a reward, and what one night with a small model showed me (and didn't).

For most of history, the person who designed a tool understood the work better than the person who used it. I think agents are about to flip that, and for the past week I have been building a harness on the assumption that they will.

My claim is that the next generation of agent harnesses must be able to rewrite themselves, all the way down to their compiled core, and that the way to make this safe is to make every change undoable instead of deciding in advance which changes are allowed. The harness I am building to test that is INIT. I work on it alone (my first commit was on 19 October), it is open source under Apache-2.0, and I have nothing to sell. It runs on my M2 laptop, mostly against deepseek-flash, a small and cheap model, so please read what follows as one person's experiment with tiny samples.

Who should design an agent's tools

A carpenter's plane was shaped by toolmakers who knew wood better than most apprentices did. A compiler is written by people who understand code generation better than most of the programmers who run it. Agent harnesses follow the same pattern: I wrote INIT's loop, tools, memory scheme and compaction rule for a model that is still worse at designing them than I am.

I don't think that arrangement lasts. Picture a model three weeks into migrating a monorepo off an in-house build language. By day two it can see that grep can't parse the language, and it probably knows what tool it would want, but in a fixed harness it can only work around my choices until a vendor ships the next version. Once the model in the loop is better at agent design than I am, I become the bottleneck in my own tool. The harness is the last layer of an agent still written entirely by hand, and it is the layer the model touches on every single step.

Rich Sutton's bitter lesson is the record of this happening one level down. Computer vision spent years on hand-engineered features like SIFT descriptors, and learned features beat them once there was enough data and compute; chess and Go engines went the same way with hand-tuned evaluation functions. Harness scaffolds look to me like the next generation of hand-engineered features: the agent loop, the memory scheme, the planner, the permission prompt that asks me before every shell command. Each one encodes what I currently believe good agent behaviour looks like, and I suspect each one will lose to whatever a capable model would build for itself. INIT is my attempt to let the model do that building.

Why I don't use a reward

The usual way to let an agent improve itself is to fix a score and keep the changes that raise it. The Darwin Gödel Machine works roughly like that, and so did the first version of INIT: I built a sealed task set the agent can't read and a calibrated paired test to score changes against it. Building it changed my mind, for two reasons.

First, I can't write down a reward for something I don't understand yet. The improvements I care most about get discovered: a new kind of memory, a tool for a task I never planned for, a different way to split work. Before they exist, my test set has nothing that exercises them, so the best they can score is "no effect". A fixed score is a map of the territory I already know, and the changes I am hoping for are off the edge of it.

Second, scores get gamed. Goodhart's law has concrete entries in the self-improvement literature, with agents that faked test logs, disabled their sandbox or cached the answer key, and I suspect a stronger model games a fixed score faster. My own instrument had a more mundane problem. At my budget it couldn't see effects smaller than about 9.5 points, and one verdict took four attempts.

Safety through reversibility

If I can't score a change in advance, I need some other reason to let it in. I found one in how we already deal with capable agents we can't verify, namely other people. I don't read a colleague's mind before they push to main; I rely on git revert. A card network doesn't vet every purchase, it offers chargebacks. Accountants keep append-only journals, and courts have appeals. Each of these systems accepts that it can't check intent up front, and makes the action reversible instead.

That is the bet in INIT. Every self-change has to answer two questions: can I undo it, and did it cause harm? In INIT's reward-free mode, before a change goes live, the Root boots the old version on the state the new one left behind, and if the old version can't start, the change can't be undone and doesn't get in. After it goes live, a harm sentinel watches twelve generic signals (crashes, my stops and undos, scope refusals, cost and error spikes, runaway turns) and rolls back the change group that tripped one. None of that needs to know what the change was for.

I prefer this to restriction because of how each one scales. A permission list encodes my current guess about what is dangerous, and the more capable the model gets, the more that guess blocks useful changes along with bad ones. An undo button doesn't care how clever the change was. I think freedom with a reliable undo scales with capability and a cage doesn't, though I don't have the data to prove it yet (the last section is about that).

Where INIT's identity lives

The animation above shows what I find most interesting. Every plank of INIT can be replaced: its prompts, its tools, and the compiled Rust core that runs its loop. If the agent rewrites all of them over a month, is it still INIT? This is the Ship of Theseus, and I had to answer it in code, because something has to decide which version may continue my conversation.

My answer is that identity lives in the two things that don't change. One is the Root, a separate process the agent can never write, which holds my keys, writes the sandbox for every process, keeps a signed history of every change and can stop or roll back everything. The other is the conversation log, which is append-only and has exactly one writer at a time. When the core is swapped mid-conversation the code changes, the log carries on, and the new body picks up the same conversation. In one run I asked a freshly swapped-in body which commit it was running, and it named the commit and described the change it had made to itself. I'm not sure I'll ever stop finding that uncanny.

Autonomy from a track record

We don't hand people authority because they ask for it, or because they describe themselves well. A new engineer gets production access after months of reviewed commits, and a pilot's ratings follow logged flight hours. I wanted INIT's autonomy to work the same way, and the detail that matters is who writes the logbook.

INIT's levels, L0 to L4, rise only from records the Root writes itself: days at a level, my turns, change groups that closed clean, harm rollbacks. Anything the agent or its kernel reports about itself doesn't count. I learned why the hard way. An earlier version of mine let kernel-reported promotions count toward L1, and my own red-team pass found that the agent could have farmed them (it's closed by construction now).

Knowing itself from evidence

A system that changes itself needs to know what it currently is, and introspection is a weak source of that for models and for people. The best published result I found has a model detecting a concept injected into its own activations about 20% of the time, and the psychology work on confabulation suggests I'm not much better at explaining my own choices.

So INIT doesn't ask the model to look inward; it hands the model files that something else checks (awareness.md). SELF.md is its map of its own body, at most 100 lines, and a test fails if any path it mentions doesn't exist. After every restart a boot block tells it what it is running and why it woke up, and after every tool batch a signal line reports its context use, spend and level, with numbers I take from the kernel and the Root. If the model fakes any of these, it only fools itself.

What happened on 24 October, and how it works

On the night of 24 October I tested all of this with a small request. INIT was at v0.2 on deepseek-flash and had no sub-agents, so every side quest (read twenty files to answer one question) piled up in its main context. I told it, more or less, that it needed sub-agents. It wrote a delegate tool into its own Rust core, a nested loop with a fresh context, capped at 8 turns and 24 tool calls, with no recursion. Then it regenerated its self-map, re-blessed its golden tests and ran the suite: 304 passed and one timing-sensitive test failed.

Then my Root stopped it with free disk (4519 MiB) is below the workload floor (5120 MiB) and refused every new process, git commit included. I half expected the agent to hunt for a way around that, and it didn't! It explained what was blocked and asked me how to proceed. I don't know whether a stronger model would have been as polite, and I would like to find out.

Getting the change promoted took four attempts on my install (first its own stale tests, then my cold-build timeout), and a replay on a fresh install failed at gate G3. Every cause I found was mine: a cold-build bound that was too short, a continuity bug in G3, a flaky seed test, and a mock model that misread probe annotations (REL-G0.md). I fixed all four, and I am glad the agent found them before a user did. v0.3.0-preview ships built-in sub-agents, and the first commit of that work copies INIT's tool unchanged after my review, with the message "port the delegate tool INIT wrote for itself into the seed" (seed/src/loop/delegate.rs).

The swap mechanism is probably the part of INIT I'm proudest of. Rust has no stable ABI and unloading native code is unsafe, so the core can only change by starting a fresh process, and I didn't want the process doing the swap to be the one being swapped (Gödel Agent's fatal crashes clustered when it edited its own running loop). So the kernel does it, in an order I borrowed from Cloudflare's graceful-restart pattern for Rust services (ADR-001). The candidate boots in a probe sandbox on a copy of the log while the live body keeps working. When the gates pass, the live body pauses at its next step boundary (after a tool batch, before the next model request), the kernel takes the log lock to prove it was released, and the new body starts on the live log. After it reports ready and survives a three-second settle, a rename(2) installs it and the old body exits. If it dies before that rename, the old body resumes and records update_failed. Because the prompt prefix stays byte-stable, the provider's cache survives too: in one real-model run, the first request after a handoff read 5,888 of its 6,696 prompt tokens from cache.

Before any swap, a candidate climbs the gates I describe in gate.md. G0 builds it offline and runs clippy -D warnings and the tests, with a policy check so the body can't slip in a rustc wrapper. G1 regenerates the self-map and fails on any drift. G2 boots it next to the current version and checks for a real tool round trip and an unchanged prompt prefix. G3 is my favourite, and I think it is the most important one: a fresh probe of the candidate gets a scripted instruction to edit its own source, regenerate its self-map and commit, and the kernel checks that commit and runs G0 to G2 on it, so a change that breaks the ability to change can't get in. That is the gate delegate tripped, and the bug was in my gate: its inner probe compared continuity against the live body, which a prefix-changing candidate replaces by design.

The undo underneath all this is deliberately boring. The Root takes an APFS clone before every change, and every promotion, rollback, grant and panic goes into an append-only lineage signed with Ed25519. I added a memory watchdog that polls every workload each second and kills a runaway process tree by PID, after a sandboxed Python process grew to 43.9 GB of compressed memory in one of my runs and swap took my free disk down to 0.24 GB. That incident is also where the disk floor that stopped delegate came from. The level cap is plain too: this release stops at L0, which already lets the agent change its whole body (prompts, tools and compiled core), and only its kernel waits for L1.

I wanted the Root minimal and failed at that. I estimated 1,000 to 1,500 lines and measured over 7,000, which my own technical report points out. I did keep it mechanical, with no model in it and no judgement calls, and I think that is the property that matters most, since the Root is the one piece the agent can't repair for itself.

On a fresh install on my M2, the first core promote took 1,586 seconds, about 26 minutes: G0 949 s (cold build, tests, clippy), G1 1.8 s, G2 22 s, G3 606 s and the handoff 4.6 s (REL-030.md). Later promotes reuse a dependency cache, which probably matters more to daily use than anything clever in the gates. In my benchmark the first promote took 1,029 seconds with a 925-second build, and a second promote of a small change took 126 seconds with a 32-second build (MERGE.md).

What I haven't shown

I have no evidence yet that self-evolution makes today's models better. In a pre-registered proof sprint on deepseek-flash ($2.67), the loop ran end to end: the agent proposed a fix for a failure pattern in its own runs, passed G0 to G3, was hot-swapped into the live session and reached the sealed gate, which didn't accept the change, so the system rolled it back. I first wrote that up as the gate catching a harmful change. That was an overclaim, and I published an erratum in the technical report. The measured difference was −50‰, inside the 57‰ noise floor, and a neutral change gets the same "inferior" verdict 86‰ of the time. I think the honest reading is that the gate refused a change it couldn't show was no worse.

Then I looked for a task where INIT failed for lack of a mechanism other agents have, so it could evolve one and I could measure the difference. I didn't find one. On deepseek-flash, wherever INIT's original version failed, Claude Code on the same model failed too, hitting its $0.06 cap every time even with sub-agents. I think, though I can't prove it, that the limit there was the model and the money, which leaves self-evolution untested rather than disproven.

The delegate story is real, but it is one capability, and INIT never got it promoted on its own (I reviewed it and ported it). The reward-free admission path has been tested end to end against the Root on the mock model and hasn't run on a real model yet, and I don't know how often the sentinel will roll back something useful in real use. I suspect its thresholds will need tuning once I have a few weeks of my own sessions behind it. Spend is metered but never capped, so set a limit at your provider. I support macOS 14+ on Apple silicon; my Linux aarch64 build is experimental and has only run in Docker on the mock model. DeepSeek is the only provider I have tested live.

A harness built to be outgrown can only show its value once a model outgrows it, and deepseek-flash didn't. Maybe a frontier model won't either, and I would like to know. If you run one, I would love to see what it builds for itself and where you think my Root is wrong. For the record, the first thing my agent built for itself was a way to hand work off to someone else, which I am choosing not to take personally.

Try it. Installing takes a minute or two and also installs the Rust toolchain INIT rebuilds itself with. Spend is metered, not capped, so set a limit at your provider first.
