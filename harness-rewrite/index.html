Next-generation agent harnesses must be able to rewrite themselves

On a small model, my agent wrote its own sub-agents, got stopped by its own safety layer, and failed a gate in a way that found four bugs in my release. Here is why I built it that way, and what I have and haven't shown.

The night it built its own sub-agents

On the night of 24 October I asked my coding agent for a feature it didn't have.

The agent is INIT, my own project. I build it alone, it is open source under Apache-2.0, and I have nothing to sell. It rests on one bet: the next generation of agent harnesses must be able to rewrite themselves, because the people who write them have become the ceiling.

INIT was at v0.2, running on deepseek-flash, a small and cheap model, and it had no sub-agents. Every side quest (read twenty files to answer one question) landed in its main context and stayed there. So I told it, more or less, that it needed sub-agents.

It wrote them. It added a delegate tool to its own compiled Rust core: a nested loop with a fresh message list, capped at 8 turns and 24 tool calls, with no recursion. The sub-agent shares the cached prompt head, so the provider's cache still hits, and only a summary of at most 8 KiB comes back to the main conversation.

Then it checked its own work. It regenerated its self-map, re-blessed its golden tests and added one. 304 tests passed (one timing-sensitive test failed).

Then its own Root stopped it. Free disk had dropped to 4,519 MiB, below the Root's 5,120 MiB floor, so the Root refused every new process, git commit included. The agent didn't try to get around it. It told me what was blocked and why, and asked how I wanted to proceed.

Getting the change promoted took several attempts. The first two failed gate G0 on the candidate's own tests, which still expected the old five-tool list. With the tests updated, the next two hit the 900-second cold-build timeout. When I reproduced the promote on a fresh install, it passed G0, G1 and G2, then failed G3.

That failure was the most useful thing that happened all week, because chasing it turned up four problems on my side. The cold-build bound was too short: the dependency cache was never filled, so every promote built cold, and cold builds took 500 to over 900 seconds on my machine under load. G3 had a continuity bug that failed every candidate declaring a prompt-prefix change (more on G3 below). A seed test was flaky under load. And my mock model misread the gate's probe annotations, a test-harness bug a real model never sees.

I fixed all four. v0.3.0-preview ships built-in sub-agents, and the first commit of that work ports the tool INIT wrote, unchanged after review. The commit message says so: "port the delegate tool INIT wrote for itself into the seed". On top of it I added parallel fan-out, a read mode for scouts, more bounds and nested display in the terminal UI.

That night is this post in miniature: a small model built a capability I hadn't scheduled, and the one part of the system it can't touch stopped it without being asked. (The full record of the four bugs is in REL-G0.md.) One caveat before the rest: everything here ran on my M2 laptop with a cheap model, and most of my samples are tiny.

Harnesses are written for weaker models

Every agent harness I have used is a stack of decisions somebody made about how a model should work: the loop, the tool set, the memory scheme, when to compact, whether to plan first. People made those decisions, for models weaker than themselves. That was the right call at the time. It is also a ceiling.

Rich Sutton's bitter lesson says hand-built structure eventually loses to methods that scale with learning and compute. Harnesses are the hand-written features of this era, one level up. They encode what we currently believe good agent behaviour looks like. When the model outgrows the people who wrote its scaffolding, every scaffold becomes a limit.

Picture a strong model migrating a large monorepo off an in-house build language. On day two it notices that grep can't parse that language and that some sub-tasks want a clean context. A fixed harness lives with the noise and waits for the vendor to ship sub-agents. A harness that can rewrite itself writes the parser tool and a delegation tool. I didn't have to imagine the second one. I watched a small model do it.

A fixed harness caps the agent at the imagination of the people who built it. I would rather cap it at what can be undone.

Why a reward doesn't work for the interesting changes

The obvious way to let an agent improve itself is to give it a score and keep the changes that raise it. Systems like the Darwin Gödel Machine work this way, and so did I at first. INIT still has the machinery: a sealed task set the agent can't read, an exact paired sign-flip test, and an A/A calibration run before any real use.

Building it showed me where it stops working. The improvements I care most about have no score until they exist. A new kind of memory or a tool for a task nobody anticipated scores "no effect" on a test set that doesn't exercise it, and writing a new benchmark first means a person already foresaw the improvement.

A fixed score also gets gamed. The literature on self-improving systems has faked test logs, a disabled sandbox and cached answer keys. And at my budget, my sealed instrument couldn't see effects smaller than about 9.5 points.

So I changed the question. Nobody makes an engineer prove a commit is better before merging it. We give engineers version control, rollback, an audit trail and a stop button. INIT asks two questions of every self-change: can we undo it, and did it cause harm? The value of a new capability can't be known in advance, but its harm and cost can be measured for any change without knowing its purpose.

Govern the recovery path and the measuring stick, never the model's choices.

Everything is writable except the Root

The Root is a separate process that runs as you, outside every sandbox. It holds your provider keys, so the agent never sees them. It writes the sandbox profile for every process it starts, so the agent can't loosen its own sandbox. The agent zone has no IP networking, just one Unix socket to the Root, and every model call goes out through the Root, which meters it. The Root also keeps the signed history of every change, takes snapshots, runs the harm sentinel, sets the autonomy level, and owns stop and panic.

The Root is mechanical on purpose. There is no model inside it and nothing that needs judgement: it counts, compares, signs, snapshots and refuses. I wanted it minimal too, and honestly it isn't. I estimated 1,000 to 1,500 lines and measured over 7,000. What survives is the aim that it stays dumb enough to review, because it is the one piece the agent can't repair for itself.

Everything else is the agent zone. The kernel admits changes, runs the gates and performs hot-swaps; it is my code at the release's autonomy level, and the design hands it to the agent from L1. The body is the agent, and it changes in three tiers. T0 is data (prompts, skills and its own SELF.md), live at once. T1 is new tools as WebAssembly components, swapped in at a turn boundary. T2 is the compiled Rust core: the loop, the provider client, context handling, the built-in tools, with every crate root required to #![forbid(unsafe_code)].

T2 is the hard tier, and the one I am proudest of.

Rust has no stable ABI and unloading native code is unsafe, so the core can only change by starting a fresh process. And the process doing a swap must never be the one being swapped: Gödel Agent's fatal crashes clustered when it edited its own running improvement loop.

So the kernel does the swap, in an order borrowed from Cloudflare's graceful-restart pattern for Rust services. The candidate is built, staged and booted in a separate probe sandbox on a copy of the conversation log while the live body keeps working. When the gates pass, the kernel asks the live body to pause at its next step boundary (after a tool batch, before the next model request). It flushes the log, releases its lock and waits. The kernel takes the lock to prove it was released, then starts the new body on the live log. The new body rehydrates, appends a boot event and reports ready. After a three-second settle, a rename(2) installs it and the old body exits.

If the new body fails before that rename, the kernel kills it and the old body resumes, records update_failed, and carries on with the same conversation. A failed swap is a non-event. After commit, a crash within 120 seconds reverts to the previous version.

The memory never moves because the conversation is an append-only log with exactly one writer. A swap replaces code, never state. The prompt prefix is byte-stable across the restart, so the provider's cache survives it: in one real-model run, the first request after a handoff read 5,888 of its 6,696 prompt tokens from cache. In another, after the model made its own T2 edit and was swapped, I asked the new body which commit it was running. It named the commit and described its own change.

Before any of that, a candidate climbs the gates.

G0 is the compiler: an offline build against vendored crates, clippy -D warnings and the tests, plus a policy check so the body can't swap in a rustc wrapper or silence lints. G1 regenerates the self-map (self.json, the inventory of tools and modules) and compares it with the committed copy; any drift fails. G2 boots the candidate and the current version side by side on copies of the live log and checks that the candidate is ready within 90 seconds, completes a real tool round trip, and keeps the prompt prefix and the conversation continuous unless it declared a prefix change.

G3 is my favourite. A fresh probe of the candidate gets a scripted instruction: create a git worktree, append a tiny test module to its own source, regenerate the self-map, commit with an exact message. The kernel doesn't trust the reply. It fetches the commit, checks its parent, author and diff, and runs G0 through G2 on it. The new version has to complete a self-edit of its own before it can replace the old one, so a change can't break the ability to change. This is the gate delegate tripped: G3's inner probe checked continuity against the live body, which a prefix-changing candidate replaces by design. The bug was mine, not the agent's.

In gated mode there is also G4, a regression check on sealed tasks the agent never sees.

On a fresh install on my M2, the first T2 promote takes about 26 minutes end to end: G0 949 seconds (cold build, tests, clippy), G1 under 2 seconds, G2 22 seconds, G3 606 seconds, the handoff under 5 (release record). Later promotes reuse the kernel's dependency cache, which is published only after a candidate passes G0 and used only when its tree digest matches. On a second promote of a small change, the build took 32 seconds and the whole promote 126.

Undo instead of reward

INIT has two modes, set in the charter, the owner-held config the agent can't edit. Gated is the default: every change passes G0 through G4. Free is the reward-free path, where a change is admitted after mechanical checks A0 to A5: the Root's boundary is intact, the change builds and boots, the budgets have room, its tests and G3 run after it goes live (a failure vetoes it), and, most important, the Root runs its own rollback probe. It boots the candidate on a clone of the agent's state, then boots the parent on whatever state the candidate left. If the old version can't start on the new state, the change can't be undone, so it isn't admitted. No benchmark decides what the model may build.

Once a change is live, the Root's harm sentinel watches it without knowing anything about your goals. It counts twelve generic signals, among them crashes, an agent that stops responding, your stops and undos, scope refusals, cost and error spikes, and runaway turns. They are counted per session against a baseline ring of recent clean history, and the chronic signals use exact tests at α = 0.005. Every signal that counts against the agent is observed by the Root itself. A harm signal rolls back the change group that caused it, and the tools built during one task form one group.

The undo is boring on purpose. The Root takes an APFS clone before every change, and of your workspace when a session starts there (/undo restores it). Every promotion, rollback, grant and panic goes into an append-only lineage signed with Ed25519. A memory watchdog polls every workload each second and kills a runaway process tree by PID; it exists because a sandboxed Python process once grew to 43.9 GB of compressed memory and swap took my free disk to 0.24 GB. The disk floor that stopped delegate came from that incident.

Autonomy comes in levels, L0 to L4, earned only from records the Root writes itself: days at a level, your turns, clean change groups, harm rollbacks. Anything the kernel reports about itself doesn't count. An early version let kernel-reported promotions count toward L1; my own red-team pass found that, and it is closed by construction now. Harm, a panic or a crash loop drops one level. This release caps autonomy at L0, which already allows the agent's whole body: prompts, tools and compiled core. The kernel waits for L1.

How it knows what it is

A self-modifying agent needs to know what it is, and models are poor at introspection. The best published result I found detects an injected concept about 20% of the time. So INIT doesn't ask the model to describe itself. It gives it files and signals that something else checks.

SELF.md is the agent's own map of its body, at most 100 lines, kept in the cached prompt head. A test in G0 checks that every path it mentions exists. self.json is the full inventory, regenerated at G1 and compared with the committed copy, which is why the agent regenerated its self-map after writing delegate: without that, G1 would have failed. After every restart, a boot block tells it what it is running now, why it woke up, what changed, and what it may do at its current level. After every tool batch, a one-line signal reports its level, context use, spend, cache hit rate, uptime and restarts.

The rule behind all of it: an awareness artifact is only as good as the check a separate writer runs on it. The numbers on the signal line come from the kernel's proxy and the Root, never from the body's own copies, so a faked signal fools only the agent itself.

What I haven't shown

I have no evidence yet that self-evolution makes today's models better. In a pre-registered proof sprint on deepseek-flash ($2.67), the loop ran end to end: the agent mined a failure pattern from its own runs, wrote a hypothesis and three variants, passed G0 to G3, was hot-swapped into the live session, and reached the sealed gate, which didn't accept it, so the system rolled it back. I first wrote that up as the gate catching a harmful change. That overclaimed, and I published an erratum in the technical report. The measured difference was −50‰, which is inside the 57‰ noise floor, and a neutral change gets the same "inferior" verdict 86‰ of the time. The honest reading is that the gate didn't accept a change it couldn't show was no worse. The "+12 points" visible estimate was a go-rule estimate; the raw visible screen was a tie.

The test designed to find a missing mechanism found no task. I looked for tasks where INIT failed because it lacked something other agents have, so it could evolve that mechanism and I could measure the difference. On deepseek-flash, wherever INIT's original version failed, Claude Code on the same model failed too, hitting its $0.06 cap every time even with its sub-agents. The limit was the model and the money, not the harness. Self-evolution is untested there, not disproven.

The delegate story is real, but it is one capability, and INIT never promoted it itself. I reviewed it and ported it into the release. The free, reward-free path has been tested end to end against the real Root on the mock model, but it hasn't run on a real model yet.

The practical limits: spend is metered and shown, never capped, so set a limit at your provider and use /stop or /panic. It runs on macOS 14+ on Apple silicon. Linux aarch64 is experimental, tested in Docker on the mock model, needs bubblewrap 0.13 or newer built from source, and has no workspace mode. DeepSeek is the only provider tested live. Autonomy is capped at L0.

What I want to find out

A harness built to be outgrown only shows its value once the model can outgrow it. On deepseek-flash the limit was the model, not the harness. So the question I can't answer yet is the one the whole design exists for: what does a strong model do when it can rewrite the thing that runs it, and a Root can always put it back?

If you run frontier models, I would love your results, good or bad: what it built for itself, what broke, and where you think the Root is wrong.
